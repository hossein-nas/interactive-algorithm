A coding interview is not a quiz where the only thing that counts is the final code. The interviewer is trying to answer one question: "Would I enjoy solving a hard problem next to this person?" They learn that from how you handle the unknown: how you ask questions, how you break a problem apart, how you react when you get stuck, and how you check your own work.

This file gives you a repeatable routine. You do not need to be a genius if you have a routine, because a routine keeps you calm when your brain wants to panic.

How to read this file: read it once now, then come back to it before every mock interview. The later topic files (two pointers, graphs, DP, …) all assume you follow this routine.

1. The whole interview on one page

Most coding rounds are 45 minutes. Here is a realistic split of that time. The exact numbers are not important; the shape is.

Notice that only about a third of the time is typing code. Candidates who start typing in minute one usually run out of time, because they have to rewrite everything when they discover a misunderstanding in minute 20.

Practice the shape with a real clock. Pick any problem, start the timer, and move on when each phase runs out.

2. The seven-step routine (memorize this)

Let's walk through each step in plain English.

Step 1 · Restate

Say the problem back in your own words, in one or two sentences.

"So I get a list of numbers and a target, and I need to return the positions of two numbers that add up to the target. Is that right?"

Why this matters: about one in five interview "failures" is simply solving a slightly different problem than the one asked. Restating costs ten seconds and catches that.

Step 2 · Clarify

Ask the questions that could change your algorithm. Do not ask random questions just to look careful. Good clarifying questions are specific. Use this checklist:

Ask aboutExample questionWhy it can change your solution
Size"Roughly how big can the input be?"20 items allows brute force; 10⁶ items demands about O(n log n) or better.
Order"Is the array sorted?"Sorted data unlocks binary search and two pointers.
Duplicates"Can values repeat?"Changes how you use sets, how you skip repeats, and what "unique" means.
Negative numbers"Can values be negative or zero?"Breaks sliding windows that assume the sum only grows.
Empty input"What if the list is empty?"Decides what you return and whether you need a guard.
Output form"Return the values, the indexes, or just a yes/no?"A Map of indexes vs. a Set of values.
No answer"What do I return if there is no valid answer?"-1, null, [], or an error.
Mutation"May I change the input in place?"Allows O(1) extra memory tricks; otherwise copy first.
Memory"Is extra memory allowed?"Sometimes the whole point is to use O(1) space.

If the interviewer says "you decide", say your assumption out loud and move on: "I'll assume the numbers are integers, can be negative, and there is exactly one answer. I'll note where that matters."

Step 3 · Example

Make a tiny example (3–6 items) and solve it by hand, out loud. Then make a second example that is tricky (duplicates, empty, one item, all the same).

The small example does two jobs. First, it proves you understand the task. Second, it often reveals the pattern. When you watch yourself solving it by hand, you notice what your own brain does ("I keep a running total", "I look at the biggest remaining item"), and that is the algorithm.

Step 4 · Brute force

Always state the simple, slow solution first, even if it is embarrassing. Say its cost.

"The brute-force way is to try every pair, which is two nested loops, so O(n²) time and O(1) space. For a million items that is far too slow, so let me look for something better."

Why bother? Three reasons:

  1. It shows you can solve the problem. You are never stuck with nothing.
  2. It gives the interviewer a baseline to compare your better idea against.
  3. The slowness of brute force points to the fix. Ask: "What work am I repeating?" Repeated work is what hash maps, sorting, prefix sums, and DP exist to remove.

Step 6 · Code

Rules for writing code in an interview:

  • Narrate in short phrases. "I'm creating a map from value to index." Silence makes interviewers nervous.
  • Use clear names. left, right, windowSum, bestLength beat i, j, s, m for anything non-trivial.
  • Write the skeleton first. Function signature, the loop, the return. Fill in the middle.
  • Handle the empty/base case at the top. This is cheap insurance.
  • Do not optimize while writing. Get a correct version first; mention improvements afterwards.
  • If you are unsure of a library function, say so: "I would use the built-in sort here; I'll assume it sorts numerically." Interviewers care about ideas, not memorizing APIs.

Step 7 · Test and analyze

Never say "I'm done" right after typing. Run your code by hand on:

  1. The small example from Step 3.
  2. An edge case (see the checklist below).
  3. A case that exercises the tricky branch: the line you were least sure about.

Then state the complexity (see Section 5).

4. Debugging when your code is wrong (it will be)

Everybody's first version has a bug. What the interviewer watches is how you find it.

A calm way to say this to the interviewer: "The output is wrong for [3,3]. Let me trace it. After the first loop left is 0 and right is 1… and here, I expected the map to hold 3, but it overwrote the index. That's the bug."

Common bug families, in rough order of how often they occur:

  1. Off by one. < vs <=, n vs n-1, whether the end of a range is inclusive.
  2. Wrong initial value. Starting a maximum at 0 when all numbers can be negative; starting a minimum at 0 instead of Infinity.
  3. Forgetting to update a variable in one branch.
  4. Mutating while iterating. Removing items from a list you are looping over.
  5. Aliasing. Two names pointing at the same array (very common when saving a result in backtracking, see file 11).
  6. Infinite loop. A pointer that never moves in some branch.
  7. Not handling the base case in recursion.

5. Complexity: how to say it

Say time and space at the end, in plain words, with the reason.

"This is O(n) time, because each element enters the window once and leaves once. It uses O(k) extra space for the map, where k is the number of distinct characters."

Three habits:

  • Give the reason, not only the symbol. "Because of the nested loops" is a reason. "Because I said so" is not.
  • Name your variables. If you have a matrix, say O(rows × cols), not O(n²).
  • Mention the trade-off. "I trade O(n) memory for O(n) time. If memory mattered, I could sort first and use two pointers."

6. What to do when you are stuck

Being stuck is normal. The interviewer expects it. What matters is that you have a procedure for it.

Concrete tricks:

  • Shrink the problem. What if the array had only 2 items? Only 3? What changes?
  • Change the input. What if it were sorted? What if there were no duplicates? Solve that, then remove the assumption.
  • Draw it. Arrays as boxes, trees as circles, a grid as a table. Pictures reveal what formulas hide.
  • Work backwards. What would the very last step of the answer look like?
  • Think about the data structure you wish you had. "If only I could look up a number instantly…" → hash map. "If only I could always grab the smallest item…" → heap.
  • Ask for a hint without shame. "I see two directions: A and B. I lean toward A because… Does that sound reasonable?" Interviewers like collaboration. A hint taken gracefully is better than ten minutes of silence.

7. A full think-aloud example

This is how a strong candidate might sound on a classic question. The words in italics are what the candidate says out loud.

Question: "Given an array of integers and a target, return the indexes of two numbers that add up to the target."

  1. Restate: "So I return two positions whose values sum to the target. Can I use the same element twice?" — "No."
  2. Clarify: "Is there always exactly one answer? Can numbers be negative? Is the array sorted?" — "One answer, negatives allowed, not sorted."
  3. Example: "For [2, 7, 11, 15] and target 9, positions 0 and 1, since 2 + 7 = 9."
  4. Brute force: "Try every pair: two loops, O(n²) time, O(1) space."
  5. Improve: "When I look at 7, what I need is 9 − 7 = 2. If I had remembered every earlier number, I could ask 'have I seen 2?' instantly. A hash map from value to index does that. One pass, O(n) time, O(n) space."
  6. Code (see below), narrating.
  7. Test: "[2,7,11,15], 9: at index 0, need 7, not seen, store 2→0. At index 1, need 2, seen at 0, return [0,1]. Edge: [3,3], 6 – at index 1, need 3, seen at 0 – correct, because I check before I store. Edge: no answer – I return an empty array."

The code that candidate would write:

Watch the candidate's words line up with the code. Switch to the brute-force version to see why step 4 comes before step 5.

function twoSumDemo(nums: number[], target: number): number[] {
  // seen maps a value to the index where we saw it.
  const seen = new Map<number, number>();
  for (let i = 0; i < nums.length; i++) {
    const need = target - nums[i];
    const j = seen.get(need);
    if (j !== undefined) return [j, i]; // found it before storing -> no self-pairing
    seen.set(nums[i], i);
  }
  return []; // the agreed "no answer" value
}

console.log(twoSumDemo([2, 7, 11, 15], 9)); // [ 0, 1 ]
console.log(twoSumDemo([3, 3], 6)); // [ 0, 1 ]
console.log(twoSumDemo([1, 2], 10)); // []
func twoSumDemo(nums []int, target int) []int {
	// seen maps a value to the index where we saw it.
	seen := make(map[int]int)
	for i, v := range nums {
		need := target - v
		if j, ok := seen[need]; ok {
			return []int{j, i} // check before storing -> no self-pairing
		}
		seen[v] = i
	}
	return []int{} // the agreed "no answer" value
}

func exampleTwoSumDemo() {
	fmt.Println(twoSumDemo([]int{2, 7, 11, 15}, 9)) // [0 1]
	fmt.Println(twoSumDemo([]int{3, 3}, 6))         // [0 1]
	fmt.Println(twoSumDemo([]int{1, 2}, 10))        // []
}

8. Testing your own code without a test framework

Interviews rarely have a test framework. Build a tiny helper in the first minute of testing, or just write the calls and the expected answers as comments. Here is a minimal version:

type Case<I extends unknown[], O> = { args: I; want: O; name: string };

function runCases<I extends unknown[], O>(fn: (...a: I) => O, cases: Case<I, O>[]): void {
  for (const c of cases) {
    const got = fn(...c.args);
    const pass = JSON.stringify(got) === JSON.stringify(c.want);
    console.log(`${pass ? "PASS" : "FAIL"} ${c.name}: got ${JSON.stringify(got)}, want ${JSON.stringify(c.want)}`);
  }
}

runCases(twoSumDemo, [
  { name: "basic", args: [[2, 7, 11, 15], 9], want: [0, 1] },
  { name: "duplicates", args: [[3, 3], 6], want: [0, 1] },
  { name: "no answer", args: [[1, 2], 10], want: [] },
]);
// PASS basic: got [0,1], want [0,1]
// PASS duplicates: got [0,1], want [0,1]
// PASS no answer: got [], want []
func sameInts(a, b []int) bool {
	if len(a) != len(b) {
		return false
	}
	for i := range a {
		if a[i] != b[i] {
			return false
		}
	}
	return true
}

func exampleRunCases() {
	cases := []struct {
		name   string
		nums   []int
		target int
		want   []int
	}{
		{"basic", []int{2, 7, 11, 15}, 9, []int{0, 1}},
		{"duplicates", []int{3, 3}, 6, []int{0, 1}},
		{"no answer", []int{1, 2}, 10, []int{}},
	}
	for _, c := range cases {
		got := twoSumDemo(c.nums, c.target)
		status := "PASS"
		if !sameInts(got, c.want) {
			status = "FAIL"
		}
		fmt.Printf("%s %s: got %v, want %v\n", status, c.name, got, c.want)
	}
	// PASS basic: got [0 1], want [0 1]
	// PASS duplicates: got [0 1], want [0 1]
	// PASS no answer: got [], want []
}

10. Anti-goals: things that make interviews go badly even when the code works

  • Silent coding. The interviewer cannot give credit for thinking they cannot hear.
  • Defensiveness. If the interviewer says "what about the empty array?", the right answer is "good catch" and a fix, not an explanation of why it should not happen.
  • Memorized answers. Reciting a solution without explaining why it works is easy to spot. Follow-up questions break it.
  • Over-engineering. No classes, no abstractions, no "what if requirements change" generality until the simple version works.
  • Giving up the brute force. A correct slow solution beats an unfinished clever one.

3 · Edge cases for strings and trees

List five edge cases for a string problem and five for a binary tree problem.

Answer

String: the empty string; one character; all the same character; upper vs. lower case; spaces and punctuation; a very long string; non-ASCII characters (accents, emoji).

Binary tree: null (empty tree); a single node; a left-only chain; a right-only chain; duplicate values; negative values; a perfect tree; a very deep tree (recursion depth).

4 · Why check before storing

Explain in two sentences why "check the map before storing the current value" avoids pairing a number with itself.

Answer

When you look up target − x before inserting x, the map holds only the numbers before the current index, so any partner it finds is a different element. If you stored first, a number equal to target / 2 (like 3 with target 6) would find its own index and pair itself.
