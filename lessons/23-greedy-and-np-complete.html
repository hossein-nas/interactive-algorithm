Greedy algorithms and NP-complete problems

Take the best-looking step, but only when you can prove it never hurts.

Book link: Grokking Algorithms, chapter 10 (the classroom scheduling problem, the knapsack problem, the set-covering problem) and appendix B (NP-hard problems). The book uses greedy methods in two ways: as an exact answer (classroom scheduling) and as an approximation when no exact fast answer is known (set covering, knapsack). This file keeps that structure and adds the interview staples: jump game, gas station, partition labels, and task scheduler.

Reach for it when

A local rule (earliest end, furthest reach, most coverage) never needs to be undone. Test a tiny counterexample first.

How to argue it

An exchange argument: swapping the greedy choice into any optimal answer keeps it optimal.

When it fails

Coin change with odd coins, 0/1 knapsack, set cover, TSP: use DP, search, or accept an approximation.

1. The idea in plain English

A greedy algorithm makes the choice that looks best right now and never looks back. It is the "grab the biggest cookie first" strategy.

Why greedy is attractive: it is simple and fast (often O(n log n), from a sort, or O(n)).

Why greedy is dangerous: "best right now" is not always best overall. Example: you want change for 6 cents with coins {1, 3, 4}. Greedy takes the biggest coin first: 4 + 1 + 1 = 3 coins. The best is 3 + 3 = 2 coins. For such problems you need dynamic programming (files 25 and 26).

When does greedy work?

It works when the problem has two properties:

  1. Greedy-choice property: some optimal solution begins with the greedy choice. (You can safely commit to the first step.)
  2. Optimal substructure: after the greedy choice, what remains is a smaller version of the same problem.

How to convince yourself (and the interviewer): the exchange argument. Take any optimal solution. If it does not use the greedy choice, show you can swap one of its choices for the greedy choice without making it worse. So an optimal solution that uses the greedy choice exists.

2. How to recognize it

  • "Maximum number of non-overlapping …", "minimum number of … to cover everything".
  • You can sort and a single pass seems enough.
  • Choosing the locally best thing never seems to hurt later; you cannot think of a counterexample.
  • The problem is a scheduling, covering, or matching problem.

If a small brute-force check disagrees with your greedy rule, abandon it: a single counterexample kills a greedy proof.

Problem 1 · Classroom Scheduling / Maximum Non-Overlapping Intervals (the book's example; LeetCode 435 as the "removal" form)

Task (the book). You have one classroom and a list of classes with start and end times. Schedule the largest possible number of classes with no overlaps. The book's classes: Art 9:00–10:00, English 9:30–10:30, Math 10:00–11:00, CS 10:30–11:30, Music 11:00–12:00 (shown here as hours).

Greedy rule. Always pick the class that ends earliest among those that do not conflict with the ones already chosen. Finishing early leaves the most room for everything else.

Why not "pick the earliest start" or "the shortest"? Counterexamples: one class running 9 to 17 starts first and blocks everything; a short class in the middle of two others can block both.

// Returns the chosen intervals (the biggest set with no overlaps).
function maxNonOverlapping(intervals: number[][]): number[][] {
  const sorted = [...intervals].sort((a, b) => a[1] - b[1]); // by END time
  const chosen: number[][] = [];
  let lastEnd = -Infinity;
  for (const [start, end] of sorted) {
    if (start >= lastEnd) { // touching at the boundary is allowed
      chosen.push([start, end]);
      lastEnd = end;
    }
  }
  return chosen;
}

function eraseOverlapIntervals(intervals: number[][]): number {
  return intervals.length - maxNonOverlapping(intervals).length;
}

// Returns the chosen intervals (the biggest set with no overlaps).
func maxNonOverlapping(intervals [][]float64) [][]float64 {
	sorted := append([][]float64(nil), intervals...)
	sort.Slice(sorted, func(i, j int) bool { return sorted[i][1] < sorted[j][1] }) // by END time
	chosen := [][]float64{}
	lastEnd := math.Inf(-1)
	for _, iv := range sorted {
		if iv[0] >= lastEnd { // touching at the boundary is allowed
			chosen = append(chosen, iv)
			lastEnd = iv[1]
		}
	}
	return chosen
}

func eraseOverlapIntervals(intervals [][]int) int {
	sorted := append([][]int(nil), intervals...)
	sort.Slice(sorted, func(i, j int) bool { return sorted[i][1] < sorted[j][1] })
	kept, lastEnd := 0, math.MinInt
	for _, iv := range sorted {
		if iv[0] >= lastEnd {
			kept++
			lastEnd = iv[1]
		}
	}
	return len(intervals) - kept
}

func exampleActivitySelection() {
	classes := [][]float64{{9, 10}, {9.5, 10.5}, {10, 11}, {10.5, 11.5}, {11, 12}} // Art, English, Math, CS, Music
	fmt.Println(maxNonOverlapping(classes))                                          // [[9 10] [10 11] [11 12]]
	fmt.Println(eraseOverlapIntervals([][]int{{1, 2}, {2, 3}, {3, 4}, {1, 3}}))      // 1
	fmt.Println(eraseOverlapIntervals([][]int{{1, 2}, {1, 2}, {1, 2}}))              // 2
	fmt.Println(eraseOverlapIntervals([][]int{{1, 2}, {2, 3}}))                      // 0
}

Complexity. Time O(n log n) (the sort), space O(n) (or O(1) extra when only counting).

Proof sketch (exchange argument). Let g be the interval ending earliest. In any optimal schedule, the first interval f ends no earlier than g. Replace f by g: since g ends no later, it still does not overlap the rest. The schedule is no worse, so some optimal schedule starts with g.

Problem 2 · Jump Game (LeetCode 55) and Jump Game II (LeetCode 45), Medium

Jump Game. nums[i] is the maximum jump length from position i. Starting at index 0, can you reach the last index? [2,3,1,1,4] → true; [3,2,1,0,4] → false.

Idea. Walk left to right keeping furthest = the farthest index reachable so far. If you ever stand on an index beyond furthest, you were stranded → false. Otherwise update furthest = max(furthest, i + nums[i]).

Jump Game II. Guaranteed reachable; find the minimum number of jumps.

Idea (BFS in disguise). Think in layers: the positions reachable with j jumps form a range. Keep currentEnd (the right edge of the layer reachable with the jumps used so far) and furthest (the furthest anything in this layer can reach). When you pass currentEnd, you must jump once more: jumps++ and currentEnd = furthest.

function canJump(nums: number[]): boolean {
  let furthest = 0;
  for (let i = 0; i < nums.length; i++) {
    if (i > furthest) return false; // we can never stand here
    furthest = Math.max(furthest, i + nums[i]);
    if (furthest >= nums.length - 1) return true;
  }
  return true;
}

function jump(nums: number[]): number {
  let jumps = 0, currentEnd = 0, furthest = 0;
  for (let i = 0; i < nums.length - 1; i++) { // never need to jump from the last index
    furthest = Math.max(furthest, i + nums[i]);
    if (i === currentEnd) { // we have used up the current layer: another jump is forced
      jumps++;
      currentEnd = furthest;
    }
  }
  return jumps;
}

console.log(jump([2, 3, 1, 1, 4]), jump([2, 3, 0, 1, 4]), jump([1])); // 2 2 0
func canJump(nums []int) bool {
	furthest := 0
	for i := 0; i < len(nums); i++ {
		if i > furthest {
			return false // we can never stand here
		}
		furthest = max(furthest, i+nums[i])
		if furthest >= len(nums)-1 {
			return true
		}
	}
	return true
}

func jump(nums []int) int {
	jumps, currentEnd, furthest := 0, 0, 0
	for i := 0; i < len(nums)-1; i++ { // never need to jump from the last index
		furthest = max(furthest, i+nums[i])
		if i == currentEnd { // we have used up the current layer: another jump is forced
			jumps++
			currentEnd = furthest
		}
	}
	return jumps
}

func exampleJumpGame() {
	fmt.Println(canJump([]int{2, 3, 1, 1, 4}), canJump([]int{3, 2, 1, 0, 4}), canJump([]int{0})) // true false true
	fmt.Println(jump([]int{2, 3, 1, 1, 4}), jump([]int{2, 3, 0, 1, 4}), jump([]int{1}))           // 2 2 0
}

Complexity. Both O(n) time, O(1) space. (A DP solution is O(n²); naming it and then improving it shows the greedy insight.)

Problem 3 · Gas Station (LeetCode 134, Medium)

Task. Gas stations are arranged in a circle. gas[i] is the fuel at station i; cost[i] is the fuel needed to drive to station i + 1. Starting with an empty tank, find the starting station from which you can complete one full loop, or −1. gas = [1,2,3,4,5], cost = [3,4,5,1,2] → 3.

Two greedy facts.

  1. If the total gas is less than the total cost, no start works → −1. If total gas ≥ total cost, a start exists (and is unique).
  2. While scanning, suppose we began at station s and the tank first goes negative at station i. Take any station k between s and i. When we passed k starting from s, we arrived with a tank of zero or more. If we had started at k instead, we would have begun with exactly zero, so we would have less fuel than before and would run out at or before i as well. So none of s … i can be the start. Reset: the next candidate start is i + 1, with an empty tank.

Trace. gas = [1,2,3,4,5], cost = [3,4,5,1,2]; net per station gas − cost = [−2, −2, −2, 3, 3]

inettank (from candidate start)Actionstart
0−2−2negative: reset1
1−2−2negative: reset2
2−2−2negative: reset3
3+33ok3
4+36ok3

Total net = 0 + ... = −6 + 6 = 0 ≥ 0 → answer start 3 ✔.

function canCompleteCircuit(gas: number[], cost: number[]): number {
  let total = 0; // net fuel over the whole loop
  let tank = 0; // net fuel since the candidate start
  let start = 0;
  for (let i = 0; i < gas.length; i++) {
    const net = gas[i] - cost[i];
    total += net;
    tank += net;
    if (tank < 0) { // we cannot reach station i + 1 from the current start
      start = i + 1; // so no station up to i can be the start
      tank = 0;
    }
  }
  return total >= 0 ? start : -1;
}
console.log(canCompleteCircuit([1, 2, 3, 4, 5], [3, 4, 5, 1, 2])); // 3
console.log(canCompleteCircuit([2, 3, 4], [3, 4, 3])); // -1
console.log(canCompleteCircuit([5], [4])); // 0
func canCompleteCircuit(gas, cost []int) int {
	total, tank, start := 0, 0, 0 // total: net over the loop; tank: net since the candidate start
	for i := range gas {
		net := gas[i] - cost[i]
		total += net
		tank += net
		if tank < 0 { // we cannot reach station i + 1 from the current start
			start = i + 1 // so no station up to i can be the start
			tank = 0
		}
	}
	if total >= 0 {
		return start
	}
	return -1
}

func exampleGasStation() {
	fmt.Println(canCompleteCircuit([]int{1, 2, 3, 4, 5}, []int{3, 4, 5, 1, 2})) // 3
	fmt.Println(canCompleteCircuit([]int{2, 3, 4}, []int{3, 4, 3}))             // -1
	fmt.Println(canCompleteCircuit([]int{5}, []int{4}))                         // 0
}

Complexity. Time O(n), space O(1).

Problem 4 · Partition Labels (LeetCode 763, Medium)

Task. Split a string into as many parts as possible so that each letter appears in at most one part. Return the part sizes. "ababcbacadefegdehijhklij" → [9, 7, 8] ("ababcbaca", "defegde", "hijhklij").

Idea. First record the last index of every letter. Then scan, keeping end = the furthest last-occurrence of any letter seen in the current part. When the scan index reaches end, nothing inside the part appears later: close the part and start a new one.

function partitionLabels(s: string): number[] {
  const last = new Map<string, number>(); // letter -> index of its last occurrence
  for (let i = 0; i < s.length; i++) last.set(s[i], i);
  const sizes: number[] = [];
  let start = 0, end = 0;
  for (let i = 0; i < s.length; i++) {
    end = Math.max(end, last.get(s[i])!); // the part must reach this letter's last occurrence
    if (i === end) { // everything inside is complete: cut here
      sizes.push(end - start + 1);
      start = i + 1;
    }
  }
  return sizes;
}
console.log(partitionLabels("ababcbacadefegdehijhklij")); // [ 9, 7, 8 ]
console.log(partitionLabels("eccbbbbdec")); // [ 10 ]
console.log(partitionLabels("abc")); // [ 1, 1, 1 ]
func partitionLabels(s string) []int {
	var last [26]int // letter -> index of its last occurrence
	for i := 0; i < len(s); i++ {
		last[s[i]-'a'] = i
	}
	sizes := []int{}
	start, end := 0, 0
	for i := 0; i < len(s); i++ {
		end = max(end, last[s[i]-'a']) // the part must reach this letter's last occurrence
		if i == end {                  // everything inside is complete: cut here
			sizes = append(sizes, end-start+1)
			start = i + 1
		}
	}
	return sizes
}

func examplePartitionLabels() {
	fmt.Println(partitionLabels("ababcbacadefegdehijhklij")) // [9 7 8]
	fmt.Println(partitionLabels("eccbbbbdec"))               // [10]
	fmt.Println(partitionLabels("abc"))                      // [1 1 1]
}

Complexity. Time O(n), space O(1) (26 letters).

Problem 5 · Task Scheduler (LeetCode 621, Medium/Hard)

Task. CPU tasks are labeled by letters. Each takes 1 unit of time. Two same-letter tasks must be at least n units apart (the CPU can be idle). Return the minimum total time. tasks = [A,A,A,B,B,B], n = 2 → 8 (A B idle A B idle A B).

Reasoning about the structure. The most frequent task is the bottleneck. Suppose A appears maxCount times. Lay out maxCount − 1 frames of length n + 1 (one A plus n slots before the next A), then a final partial frame holding the last A (and any other tasks that also have maxCount occurrences).

Fill the blanks with other tasks. Formula:

time = (maxCount − 1) × (n + 1) + (number of tasks that have the maximum frequency)

But if there are so many different tasks that the blanks overflow (no idle needed), the answer is just the number of tasks. So answer = max(formula, tasks.length).

Trace. A A A B B B, n = 2: maxCount = 3, two tasks tie for the max (A and B).

(3 − 1) × (2 + 1) + 2 = 2 × 3 + 2 = 8 ✔. tasks.length = 6, so the answer is max(8, 6) = 8.

Another: n = 0 → (3−1)×1 + 2 = 4, but there are 6 tasks, so the answer is 6 (no idle needed).

function leastInterval(tasks: string[], n: number): number {
  const counts = new Map<string, number>();
  for (const t of tasks) counts.set(t, (counts.get(t) ?? 0) + 1);
  const maxCount = Math.max(...counts.values());
  let tied = 0; // how many task types have the maximum frequency
  for (const c of counts.values()) if (c === maxCount) tied++;
  const frames = (maxCount - 1) * (n + 1) + tied; // the layout with the necessary idle slots
  return Math.max(frames, tasks.length); // with enough variety, no idling is needed
}
console.log(leastInterval(["A", "A", "A", "B", "B", "B"], 2)); // 8
console.log(leastInterval(["A", "A", "A", "B", "B", "B"], 0)); // 6
console.log(leastInterval(["A", "A", "A", "A", "A", "A", "B", "C", "D", "E", "F", "G"], 2)); // 16
console.log(leastInterval(["A"], 5)); // 1
func leastInterval(tasks []byte, n int) int {
	var counts [26]int
	for _, t := range tasks {
		counts[t-'A']++
	}
	maxCount := 0
	for _, c := range counts {
		maxCount = max(maxCount, c)
	}
	tied := 0 // how many task types have the maximum frequency
	for _, c := range counts {
		if c == maxCount {
			tied++
		}
	}
	frames := (maxCount-1)*(n+1) + tied // the layout with the necessary idle slots
	return max(frames, len(tasks))      // with enough variety, no idling is needed
}

func exampleLeastInterval() {
	fmt.Println(leastInterval([]byte("AAABBB"), 2))         // 8
	fmt.Println(leastInterval([]byte("AAABBB"), 0))         // 6
	fmt.Println(leastInterval([]byte("AAAAAABCDEFG"), 2))   // 16
	fmt.Println(leastInterval([]byte("A"), 5))              // 1
}

Complexity. Time O(T), space O(1).

The heap version (the one most people write first, and a good fallback): repeatedly take the n + 1 most frequent remaining tasks (max-heap), run one of each, decrement counts, and re-insert the survivors; count idle slots when fewer than n + 1 distinct tasks remain. Problem 6 · The set-covering problem (the book's radio stations), and why greedy is only an approximation

Task (from the book). You want to broadcast a radio show to 8 states. Several stations each cover some states. Choose the fewest stations that together cover all 8 states.

StationStates covered
koneid, nv, ut
ktwowa, id, mt
kthreeor, nv, ca
kfournv, ut
kfiveca, az

States needed: mt, wa, or, id, nv, ut, ca, az.

The exact approach is too slow. With n stations there are 2ⁿ subsets to check. For 100 stations that is more than a nonillion possibilities. This problem is NP-complete (see the next section): no known algorithm is fast on all inputs.

The greedy approximation. Repeatedly pick the station that covers the most still-uncovered states; remove what it covered; repeat until nothing is uncovered. Fast (O(stations × states) per pick) and close to optimal (provably within a ln n factor), though not always optimal.

A tiny example where greedy is not optimal. Universe {1..6}; sets T = {1,2,4,5} (the tempting big one), O1 = {1,2,3}, O2 = {4,5,6}. Greedy picks T first (4 new items), then still needs 3 and 6: it must add both O1 and O2 → 3 sets. The optimum is just O1 + O2 → 2 sets. Greedy is fast, not perfect.

function greedySetCover(universe: string[], sets: Map<string, Set<string>>): string[] | null {
  const uncovered = new Set(universe);
  const chosen: string[] = [];
  while (uncovered.size > 0) {
    let bestName: string | null = null;
    let bestGain = 0;
    for (const [name, covers] of sets) {
      let gain = 0;
      for (const item of covers) if (uncovered.has(item)) gain++; // how much NEW coverage?
      if (gain > bestGain) {
        bestGain = gain;
        bestName = name;
      }
    }
    if (bestName === null) return null; // some item cannot be covered by any set
    chosen.push(bestName);
    for (const item of sets.get(bestName)!) uncovered.delete(item);
  }
  return chosen;
}

  ["kthree", new Set(["or", "nv", "ca"])],
  ["kfour", new Set(["nv", "ut"])],
  ["kfive", new Set(["ca", "az"])],
]);

type namedSet struct {
	name   string
	covers []string
}

func greedySetCover(universe []string, sets []namedSet) ([]string, bool) {
	uncovered := make(map[string]bool, len(universe))
	for _, u := range universe {
		uncovered[u] = true
	}
	chosen := []string{}
	for len(uncovered) > 0 {
		bestIdx, bestGain := -1, 0
		for i, s := range sets {
			gain := 0
			for _, item := range s.covers {
				if uncovered[item] {
					gain++ // how much NEW coverage?
				}
			}
			if gain > bestGain {
				bestGain, bestIdx = gain, i
			}
		}
		if bestIdx == -1 {
			return nil, false // some item cannot be covered by any set
		}
		chosen = append(chosen, sets[bestIdx].name)
		for _, item := range sets[bestIdx].covers {
			delete(uncovered, item)
		}
	}
	return chosen, true
}

		{"kfour", []string{"nv", "ut"}},
		{"kfive", []string{"ca", "az"}},
	}
	fmt.Println(greedySetCover([]string{"mt", "wa", "or", "id", "nv", "ut", "ca", "az"}, stations))

}

Complexity. Time O(picks × sets × set size), space O(universe).

4. The knapsack problem: greedy fails, DP wins

(The book uses this problem in both chapter 10 and chapter 11.)

You have a bag that holds 4 lb. Items: guitar (1 lb, $1500), stereo (4 lb, $3000), laptop (3 lb, $2000). Which to take to maximize value?

  • Greedy by value: take the most valuable item first, the stereo ($3000), which fills the bag. Total $3000.
  • Best: guitar + laptop (1 + 3 = 4 lb) = $3500.

Greedy is only an approximation here. (If you could take fractions of items, greedy by value-per-pound would be exactly optimal: that is the "fractional knapsack", a true greedy problem. The all-or-nothing version needs dynamic programming: file 26.)

type Item = { name: string; weight: number; value: number };
const loot: Item[] = [
  { name: "guitar", weight: 1, value: 1500 },
  { name: "stereo", weight: 4, value: 3000 },
  { name: "laptop", weight: 3, value: 2000 },
];

function greedyByValue(items: Item[], capacity: number): number {
  let total = 0, room = capacity;
  for (const item of [...items].sort((a, b) => b.value - a.value)) {
    if (item.weight <= room) {
      total += item.value;
      room -= item.weight;
    }
  }
  return total;
}

// Try every subset (2^n): fine for 3 items, impossible for 100.
function bestByBruteForce(items: Item[], capacity: number): number {
  let best = 0;
  for (let mask = 0; mask < 1 << items.length; mask++) {
    let w = 0, v = 0;
    for (let i = 0; i < items.length; i++) {
      if (mask & (1 << i)) {
        w += items[i].weight;
        v += items[i].value;
      }
    }
    if (w <= capacity) best = Math.max(best, v);
  }
  return best;
}

console.log(bestByBruteForce(loot, 4)); // 3500
type Item struct {
	name          string
	weight, value int
}

func greedyByValue(items []Item, capacity int) int {
	sorted := append([]Item(nil), items...)
	sort.Slice(sorted, func(i, j int) bool { return sorted[i].value > sorted[j].value })
	total, room := 0, capacity
	for _, item := range sorted {
		if item.weight <= room {
			total += item.value
			room -= item.weight
		}
	}
	return total
}

// Try every subset (2^n): fine for 3 items, impossible for 100.
func bestByBruteForce(items []Item, capacity int) int {
	best := 0
	for mask := 0; mask < 1<<len(items); mask++ {
		w, v := 0, 0
		for i, item := range items {
			if mask&(1<<i) != 0 {
				w += item.weight
				v += item.value
			}
		}
		if w <= capacity {
			best = max(best, v)
		}
	}
	return best
}

	loot := []Item{{"guitar", 1, 1500}, {"stereo", 4, 3000}, {"laptop", 3, 2000}}
	fmt.Println(greedyByValue(loot, 4))     // 3000
	fmt.Println(bestByBruteForce(loot, 4)) // 3500
}

5. NP-complete problems: when no fast exact algorithm is known

What are they?

Some problems (the book's examples: the traveling salesperson, set covering, and the knapsack decision problem) share a nasty property: nobody has found an algorithm that solves them fast in all cases, and most experts believe none exists. They are called NP-complete.

The traveling salesperson problem (TSP). A salesperson must visit n cities exactly once and return home, with the shortest total distance. The brute force tries every ordering: n! possibilities.

The vocabulary (simply)

TermPlain meaning
PProblems that can be solved quickly (in polynomial time, like n²).
NPProblems whose answer can be checked quickly once someone hands it to you.
NP-completeThe hardest problems in NP: if you could solve any one of them fast, you could solve all of NP fast.
NP-hardAt least as hard as NP-complete (may not even have quickly checkable answers).
P vs NPThe famous open question: is every quickly-checkable problem also quickly solvable? Nobody knows.

How to spot an NP-complete problem (the book's checklist)

  • Your algorithm runs fast with a few items but becomes terribly slow as items are added.
  • The problem says "all combinations of X" or "all permutations of X" and you must pick the best.
  • You cannot break it into smaller sub-problems; you must consider every possibility.
  • It involves a sequence (like cities) or a set (like radio stations) and is hard.
  • You can restate it as the set-covering or traveling salesperson problem.

What to do about it

  • Use an approximation algorithm: fast, near-optimal (greedy set cover; the nearest neighbor tour for TSP).
  • Use heuristics / local search: simulated annealing, genetic algorithms.
  • Solve small instances exactly: backtracking with pruning, DP over subsets (bitmask DP: TSP in O(2ⁿ · n²), fine for n ≤ 20).
  • Restrict the problem: special structures (a tree, small weights) can be easy.

In an interview

If you realize the problem is NP-hard, say so, then ask about constraints: "If n is small (≤ 20) I'd use bitmask DP or backtracking; if n is large I'd propose a greedy approximation and explain its guarantee." That answer shows maturity.

Common mistakes

  • Assuming greedy works without testing a tiny counterexample (coin change with {1, 3, 4}).
  • Sorting by the wrong key (intervals: end time, not start time or length).
  • Strict vs. non-strict comparison on interval boundaries (start >= lastEnd allows touching intervals; ask).
  • Resetting the wrong thing in Gas Station (reset the tank and move the start to i + 1).
  • Task Scheduler: forgetting max(formula, tasks.length), or forgetting to count ties for the maximum frequency.
  • Treating an NP-hard problem as solvable exactly at large n.
  • Not stating the greedy proof idea. Even one sentence of "exchange argument" makes the answer convincing.

1 · When greedy change-making fails

Give a coin system where greedy change-making fails, and one (like US coins) where it works.

Answer

Coins {1, 3, 4}, amount 6: greedy takes 4 + 1 + 1 (3 coins), but 3 + 3 uses 2. With US coins {1, 5, 10, 25} greedy is always optimal (each coin is worth enough of the smaller ones that taking it never hurts). For an arbitrary coin set, use DP (lesson 25).

2 · Assign Cookies

Assign Cookies (LeetCode 455): children have greed factors, cookies have sizes. Sort both; what is the greedy rule?

Answer

Sort children by greed and cookies by size. Two pointers: give the current (least greedy) child the smallest cookie that satisfies them; if a cookie is too small for this child, it is too small for everyone after, so skip it. Count the matches. O(n log n + m log m).

3 · Minimum arrows for balloons

Merge Intervals is not quite greedy; Minimum Number of Arrows to Burst Balloons (LeetCode 452) is. What do you sort by, and what do you track?

Answer

Sort balloons by end. Shoot the first arrow at the first balloon's end; it bursts every balloon whose start ≤ that point. When a balloon starts after the arrow, shoot a new arrow at its end. Track only the last arrow's position. It is activity selection again: the arrows are the chosen non-overlapping representatives.

4 · Boats to Save People

Boats to Save People (LeetCode 881): two pointers on a sorted array. Why pair the heaviest with the lightest?

Answer

The heaviest person must go in some boat. The best partner for them is the lightest person: if even the lightest does not fit, nobody does, so the heaviest goes alone. If the lightest fits, pairing them uses the least capacity and leaves heavier people more options. Sort, then move the two pointers inward.

5 · Fractional versus 0/1 knapsack

Why is the "fractional knapsack" greedy-solvable but the 0/1 knapsack is not?

Answer

With fractions you can always fill the remaining room with the item of the best value per weight, so taking that first is never wrong (exchange argument). With whole items, a high-ratio item can leave room that nothing else fits, as the last animation shows (stereo 3000 versus guitar + laptop 3500). 0/1 needs DP over capacities.

6 · Fast TSP?

A friend says "my algorithm solves TSP quickly for 1,000 cities." What two questions do you ask? (Exact or approximate? How close to optimal is it guaranteed?)

Answer

Ask: is it exact or approximate (a heuristic like nearest neighbor or 2-opt), and how close to optimal is it guaranteed, or was it just measured on some inputs? An exact polynomial algorithm would prove P = NP.
