Big O and complexity

How the work grows as the input grows, and how to read it straight from code.

Book link: Grokking Algorithms, chapter 1 (binary search and Big O notation) and the "Big O revisited" part of chapter 4. The one question

If the input gets 10 times bigger, how much more work does the code do?

Shrinking inner loops, pointers that only move forward, and built-ins that hide a loop.

1. The idea in plain English

When you ask "how fast is this code?", the honest answer depends on the computer, the language, and the input. That is useless for comparing ideas. So computer scientists ask a better question:

"If I make the input 10 times bigger, how much more work does the code do?"

That is all Big O is. It describes how the amount of work grows as the input grows. It ignores the exact seconds.

An everyday comparison. Imagine you must find one name in a phone book.

  • Way 1: read every name from page 1. Double the book, double the work. That growth is linear: O(n).
  • Way 2: open in the middle, see if your name is before or after, discard half, repeat. Double the book and you need only one extra step. That growth is logarithmic: O(log n).

For a book with 1,000,000 names, way 1 may need up to 1,000,000 looks. Way 2 needs about 20. That difference is why we care.

How big can n be? (the interview "speed limit")

Computers do very roughly 10⁸ to 10⁹ simple operations per second. Interviews and online judges usually allow about one second. So the input size tells you which complexity you need:

If n is up to…You probably need…
10–12O(n!) can be fine (permutations)
20–25O(2ⁿ) is fine (all subsets, simple backtracking)
500O(n³) is fine
5,000O(n²) is fine
10⁵–10⁶O(n log n) or O(n)
10⁹ or moreO(log n) or O(1) (binary search on a number, or math)

This is a clarifying question you should ask in every interview: "How large can the input be?" The answer tells you what is allowed.

3. The three simplification rules

Big O describes the shape of growth, so we simplify. There are only three rules.

Rule 1: drop constants. A loop that does 3 things per item is still O(n). O(2n) is O(n). Constants matter in real life, but not for the growth shape.

Rule 2: keep the biggest term. If your code takes n² + 5n + 100 steps, then for big n the n² part is all that matters. The answer is O(n²).

Rule 3: use a different letter for each independent input. If you loop over array A (size a) and then over array B (size b), the cost is O(a + b), not O(n). If you nest them, it is O(a × b). Interviewers love this because candidates often write O(n²) when the truth is O(rows × cols).

Add vs. multiply:

  • Steps one after another → add.
  • Steps inside another → multiply.

4. Reading code and finding its complexity

Here are the patterns, from easiest to trickiest. Each one has a small example in both languages. They are all runnable.

4.1 Sequential and nested loops

// O(n): one loop.
function sumAll(nums: number[]): number {
  let total = 0;
  for (const x of nums) total += x;
  return total;
}

// O(n): two loops one AFTER the other -> n + n = 2n -> O(n).
function minAndMax(nums: number[]): [number, number] {
  let lo = Infinity, hi = -Infinity;
  for (const x of nums) lo = Math.min(lo, x);
  for (const x of nums) hi = Math.max(hi, x);
  return [lo, hi];
}

// O(n^2): loop INSIDE a loop -> n * n.
function countPairsWithSum(nums: number[], target: number): number {
  let count = 0;
  for (let i = 0; i < nums.length; i++) {
    for (let j = i + 1; j < nums.length; j++) {
      if (nums[i] + nums[j] === target) count++;
    }
  }
  return count;
}

// O(a + b): two independent inputs, one after the other.
// O(a * b) if we nested them. Different letters for different inputs.
function countCommon(a: number[], b: number[]): number {
  const set = new Set(a); // O(a)
  let count = 0;
  for (const x of b) if (set.has(x)) count++; // O(b)
  return count; // total O(a + b)
}

console.log(minAndMax([4, -2, 9])); // [ -2, 9 ]
console.log(countPairsWithSum([1, 2, 3, 4], 5)); // 2
console.log(countCommon([1, 2, 3], [2, 3, 4])); // 2

	count := 0
	for i := 0; i < len(nums); i++ {
		for j := i + 1; j < len(nums); j++ {
			if nums[i]+nums[j] == target {
				count++
			}
		}
	}
	return count
}

// O(a + b): two independent inputs, one after the other.
func countCommon(a, b []int) int {
	set := make(map[int]struct{}, len(a))
	for _, x := range a { // O(a)
		set[x] = struct{}{}
	}
	count := 0
	for _, x := range b { // O(b)
		if _, ok := set[x]; ok {
			count++
		}
	}
	return count // total O(a + b)
}

func exampleLoopShapes() {
	fmt.Println(sumAll([]int{1, 2, 3})) // 6
	lo, hi := minAndMax([]int{4, -2, 9})
	fmt.Println(lo, hi)                                      // -2 9
	fmt.Println(countPairsWithSum([]int{1, 2, 3, 4}, 5))     // 2
	fmt.Println(countCommon([]int{1, 2, 3}, []int{2, 3, 4})) // 2
}

Why j = i + 1 is still O(n²): the inner loop runs n-1, then n-2, … then 0 times. That sum is n(n-1)/2, which is about n²/2. Drop the constant 1/2 (rule 1) and you get O(n²).

4.2 Loops that halve or double: logarithms

If a loop cuts the remaining work in half each time, it runs about log₂ n times. Why? Ask: "How many times can I halve 1,000,000 before I reach 1?" About 20 times (since 2²⁰ ≈ 1,000,000).

That is 4 halvings for 16 items, and log₂ 16 = 4. If you doubled the input to 32 you would get just one more step.

// O(log n): the work left is cut in half each pass.
function countHalvings(n: number): number {
  let steps = 0;
  while (n > 1) {
    n = Math.floor(n / 2);
    steps++;
  }
  return steps;
}

// O(n): the classic trap. The loop runs log n times, but each pass
// does work proportional to what is left: n + n/2 + n/4 + ... = 2n -> O(n).
function halvingWithWork(n: number): number {
  let work = 0;
  for (let size = n; size >= 1; size = Math.floor(size / 2)) {
    for (let i = 0; i < size; i++) work++;
  }
  return work;
}

console.log(countHalvings(16)); // 4
console.log(countHalvings(1_000_000)); // 19
console.log(halvingWithWork(1024)); // 2047  (about 2n, so O(n))
// O(log n): the work left is cut in half each pass.
func countHalvings(n int) int {
	steps := 0
	for n > 1 {
		n /= 2
		steps++
	}
	return steps
}

// O(n): n + n/2 + n/4 + ... = 2n.
func halvingWithWork(n int) int {
	work := 0
	for size := n; size >= 1; size /= 2 {
		for i := 0; i < size; i++ {
			work++
		}
	}
	return work
}

func exampleHalving() {
	fmt.Println(countHalvings(16))        // 4
	fmt.Println(countHalvings(1_000_000)) // 19
	fmt.Println(halvingWithWork(1024))    // 2047
}

The second function is a famous trap. The outer loop runs log n times, so many people write O(n log n). But the inner loop shrinks each time. Adding n + n/2 + n/4 + … gives about 2n, so the true answer is O(n). Always check whether the inner loop's size depends on the outer loop.

4.3 A loop that does a log-sized job each time: O(n log n)

Sorting is the main example. A good sort splits the array in half repeatedly (log n levels), and every level touches all n items.

4.4 Recursion: draw the call tree

For recursive code, draw a tree where each node is one call. Then answer two questions:

  1. How many nodes are in the tree? That is roughly the time.
  2. How deep is the tree? That is the extra memory (call stack).

Notice fib(2) appears twice. For fib(n) each call makes two more, so the tree roughly doubles at every level: O(2ⁿ) time. The depth is only n, so the stack memory is O(n). The waste here (calling fib(2) twice) is exactly what dynamic programming fixes (files 25 and 26).

let naiveCalls = 0;
function fibNaive(n: number): number {
  naiveCalls++;
  if (n < 2) return n;
  return fibNaive(n - 1) + fibNaive(n - 2); // two calls -> tree doubles -> O(2^n)
}

function fibMemo(n: number, memo = new Map<number, number>()): number {
  if (n < 2) return n;
  const saved = memo.get(n);
  if (saved !== undefined) return saved;
  const result = fibMemo(n - 1, memo) + fibMemo(n - 2, memo);
  memo.set(n, result);
  return result; // each n computed once -> O(n)
}

console.log(fibNaive(20), "calls:", naiveCalls); // 6765 calls: 21891
console.log(fibMemo(20)); // 6765
console.log(fibMemo(70)); // 190392490709135
// fib(80) would print 23416728348467684 in TypeScript: it is above
// Number.MAX_SAFE_INTEGER (2^53 - 1), so a number can no longer be exact.
var naiveCalls int

func fibNaive(n int) int {
	naiveCalls++
	if n < 2 {
		return n
	}
	return fibNaive(n-1) + fibNaive(n-2) // two calls -> tree doubles -> O(2^n)
}

func fibMemo(n int, memo map[int]int) int {
	if n < 2 {
		return n
	}
	if v, ok := memo[n]; ok {
		return v
	}
	memo[n] = fibMemo(n-1, memo) + fibMemo(n-2, memo)
	return memo[n] // each n computed once -> O(n)
}

func exampleFib() {
	fmt.Println(fibNaive(20), "calls:", naiveCalls) // 6765 calls: 21891
	fmt.Println(fibMemo(20, map[int]int{}))          // 6765
	fmt.Println(fibMemo(70, map[int]int{}))          // 190392490709135
	// Go int is 64-bit, so fib(80) = 23416728348467685 is still exact here.
}

5. Best, worst, and average case

The same algorithm can behave differently on different inputs. Searching a list for a value with a loop:

  • Best case: the value is first → 1 step → O(1).
  • Worst case: the value is last or missing → n steps → O(n).
  • Average case: about n/2 steps → still O(n).

Unless told otherwise, Big O means the worst case. But you should mention when the average differs. Two famous examples:

AlgorithmWorstAverageWhat triggers the worst case
Hash map lookupO(n)O(1)Many keys collide into the same bucket
QuicksortO(n²)O(n log n)Always picking the smallest or largest item as the pivot
BST searchO(n)O(log n)Inserting already-sorted data makes a chain

Interview habit: "Hash map operations are O(1) on average; in the worst case they degrade, but that is rare with a good hash function."

6. Amortized cost: "expensive sometimes, cheap on average"

Some operations are cheap almost always and expensive once in a while. Amortized cost spreads the rare expensive moment across the many cheap ones.

The classic example is a dynamic array (push in TypeScript, append in Go). When the array is full, it allocates a bigger one (about double) and copies everything. That single copy costs O(n). But it only happens after n cheap pushes, so averaged out each push costs O(1).

Where this shows up in interviews:

  • Sliding window / two pointers: the inner while loop looks like it makes the code O(n²). But each element is added once and removed once, so the total work across the whole run is O(n). (Amortized thinking.)
  • Monotonic stack: every item is pushed once and popped at most once → O(n).
  • Union-find: nearly O(1) per operation, amortized.

7. Space complexity

Space complexity counts the extra memory your algorithm needs as n grows. It does not count the input itself (unless the problem says to).

What uses memoryCost
A few variablesO(1)
A new array, set, or map with up to n itemsO(n)
A rows × cols tableO(rows × cols)
The recursion call stackO(recursion depth)
The output (some interviewers count it, some do not)say which you count

Recursion uses memory even with no arrays. Every call that has not finished waits on the call stack, holding its variables. A recursive function that goes n levels deep uses O(n) space, even if it creates no data structure. This is a favorite follow-up. File 10 explains the stack in detail.

In-place tricks: many "optimize the space" follow-ups ask you to go from O(n) to O(1) by reusing the input array or by keeping only the last few values (rolling variables). Two pointers and DP-with-two-variables are the usual answers.

Problem A · The "innocent" shift

function processQueue(items: number[]): number {
  let total = 0;
  while (items.length > 0) {
    const first = items.shift()!; // look closely at this line
    total += first;
  }
  return total;
}
console.log(processQueue([1, 2, 3, 4])); // 10
func processQueue(items []int) int {
	total := 0
	for len(items) > 0 {
		first := items[0]
		items = items[1:] // look closely at this line
		total += first
	}
	return total
}

func exampleProcessQueue() {
	fmt.Println(processQueue([]int{1, 2, 3, 4})) // 10
}
Answer
  • TypeScript: shift() is O(n) (it moves all remaining items), and it runs n times, so the total is O(n²) time, O(1) space. Fix: loop with an index (for (const x of items)) or keep a head pointer.
  • Go: items = items[1:] is O(1) because it only moves the start of the slice. Total is O(n) time, O(1) space.

This is a great illustration of the same-looking idea having different costs in each language.

Problem B · Triangle loops

function triangle(n: number): number {
  let count = 0;
  for (let i = 0; i < n; i++) {
    for (let j = 0; j < i; j++) count++;
  }
  return count;
}
console.log(triangle(5)); // 10
func triangle(n int) int {
	count := 0
	for i := 0; i < n; i++ {
		for j := 0; j < i; j++ {
			count++
		}
	}
	return count
}

func exampleTriangle() {
	fmt.Println(triangle(5)) // 10
}
Answer

The inner loop runs 0 + 1 + 2 + … + (n-1) = n(n-1)/2 times. For n = 5 that is 10, matching the output. Drop the 1/2 and the lower term: O(n²) time, O(1) space.

Problem C · The doubling loop and a hash map

function countDigitsPairs(nums: number[]): number {
  const seen = new Map<number, number>();
  for (const x of nums) seen.set(x, (seen.get(x) ?? 0) + 1); // line 1

func countDigitsPairs(nums []int) int {
	seen := make(map[int]int)
	for _, x := range nums { // line 1
		seen[x]++
	}
	pairs := 0

func exampleCountPairs() {
	fmt.Println(countDigitsPairs([]int{1, 1, 1, 2, 2})) // 4
}
Answer

Line 1 loops n times with O(1) average map work. Line 2 loops over the distinct keys (at most n). They are one after the other, so add: O(n) time. The map can hold up to n distinct keys: O(n) space. (Three 1s give 3 pairs, two 2s give 1 pair: total 4.)

Problem D · Recursion with branching

function countSubsets(items: number[], index = 0): number {
  if (index === items.length) return 1;
  const without = countSubsets(items, index + 1); // skip this item
  const withIt = countSubsets(items, index + 1); // take this item
  return without + withIt;
}
console.log(countSubsets([1, 2, 3])); // 8
func countSubsets(items []int, index int) int {
	if index == len(items) {
		return 1
	}
	without := countSubsets(items, index+1) // skip this item
	withIt := countSubsets(items, index+1)  // take this item
	return without + withIt
}

func exampleCountSubsets() {
	fmt.Println(countSubsets([]int{1, 2, 3}, 0)) // 8
}
Answer

Each call makes two calls, and there are n levels, so the call tree has about 2ⁿ leaves: O(2ⁿ) time. The tree is only n levels deep, so the call stack uses O(n) space. This "take it or skip it" shape is the root of backtracking (file 11).

Problem E · Nested loop that is not quadratic

// Sliding window: longest run with at most `limit` zeros.
function longestAtMostKZeros(bits: number[], limit: number): number {
  let left = 0, zeros = 0, best = 0;
  for (let right = 0; right < bits.length; right++) {
    if (bits[right] === 0) zeros++;
    while (zeros > limit) {          // a loop inside a loop...
      if (bits[left] === 0) zeros--;
      left++;
    }
    best = Math.max(best, right - left + 1);
  }
  return best;
}
console.log(longestAtMostKZeros([1, 0, 1, 1, 0, 1], 1)); // 4
func longestAtMostKZeros(bits []int, limit int) int {
	left, zeros, best := 0, 0, 0
	for right := 0; right < len(bits); right++ {
		if bits[right] == 0 {
			zeros++
		}
		for zeros > limit { // a loop inside a loop...
			if bits[left] == 0 {
				zeros--
			}
			left++
		}
		if right-left+1 > best {
			best = right - left + 1
		}
	}
	return best
}

func exampleLongestAtMostKZeros() {
	fmt.Println(longestAtMostKZeros([]int{1, 0, 1, 1, 0, 1}, 1)) // 4
}
Answer

It looks quadratic, but left only ever moves forward and never moves backward. Across the whole run, right takes n steps and left takes at most n steps in total. That is n + n = 2n, so O(n) time (amortized), O(1) space. Count how many times each pointer moves in total, not how deeply the loops are nested.

Common mistakes

  • Writing O(n²) when two different inputs are involved (O(a × b)).
  • Forgetting recursion stack memory when saying "O(1) space".
  • Calling a nested loop quadratic when the pointers only move forward (amortized O(n)).
  • Treating O(1) hash map time as a guarantee instead of an average.
  • Using shift(), string +=, or array slice inside a loop and not counting their cost.
  • Saying a log-factor loop is O(n log n) when the inner work shrinks (Problem in 4.2).

1 · Why binary search needs about 20 steps

Explain, in plain words and without symbols, why binary search takes only about 20 steps for a million items.

Answer

Each look throws away half of what is left. Starting from a million, after one look about half a million remain, after two a quarter of a million, and so on. Halving a million until one item is left takes about 20 halvings, because doubling 1 twenty times gives about a million. A book twice as big needs only one more look.

2 · Why building a heap is O(n)

Why is the time of building a heap from n items O(n) and not O(n log n)? (We revisit this in file 17; try reasoning from the "halving with work" example.)

Hint

Most nodes sit near the bottom of the tree. How far can a node near the bottom move?

Answer

Heapify sifts each node down, starting from the last parent. A node can only move as far as its height. Half of the nodes are leaves and move 0 steps, a quarter move at most 1, an eighth at most 2, and so on. The total is n/4 · 1 + n/8 · 2 + n/16 · 3 + …, which adds up to less than n. This is the same shape as the halving-with-work loop: the big work happens on few nodes, so the sum is O(n), not O(n log n).

3 · Four costs to state

State the Big O of: reversing a string with += in a loop (TypeScript), joining with strings.Builder (Go), Array.includes inside a loop, sorting then scanning once.

Answer
  • Reversing a string with += in a loop (TypeScript): each += may copy the whole string so far, so it can reach O(n²). Collect characters in an array and join.
  • Joining with strings.Builder (Go): amortized O(1) per write, O(n) total.
  • Array.includes inside a loop: O(n · m), because includes is a hidden loop. Use a Set for O(n + m).
  • Sorting, then scanning once: O(n log n) + O(n) = O(n log n).

4 · The call tree for fib(5)

Draw the call tree for fib(5). How many calls are made?

Hint

fib(5) calls fib(4) and fib(3). You already know how many calls fib(4) and fib(3) make.

Answer

15 calls. calls(n) = 1 + calls(n − 1) + calls(n − 2), with calls(0) = calls(1) = 1: so calls(2) = 3, calls(3) = 5, calls(4) = 9, calls(5) = 15. Check it by setting the call-tree animation in section 4.4 to 5: it ends with "15 calls". With the memo it drops to 9.

Check yourself
