2. How each topic file is built

Every topic file follows the same shape, so you always know where to look:

Reading the code

  • Every solution has two collapsed sections: one TypeScript, one Go. Click the arrow to open the one you want. (They are collapsible HTML details blocks; they work in VS Code's Markdown preview and on GitHub.)
  • Output is shown in comments after each call, for example // [ 0, 1 ]. In Go these calls live inside functions named exampleSomething(); that is just a convention so a test harness can run them.
  • Diagrams are Mermaid and render in VS Code (built-in Markdown preview supports Mermaid in recent versions, or install a Mermaid extension) and on GitHub.

Running the code yourself

The snippets within one file are written to be combined into one program: the names are unique per file.

The easy way: use the included checker. From inside this folder:

python3 tools/verify.py "05 two-pointers.md" --show

It extracts every ts and go block from the file, compiles them (tsc --strict, go vet), runs the examples, and prints their output. Requirements: python3, node, tsc (TypeScript), and go on your PATH.

By hand (TypeScript):

# once:  npm install -g typescript   (Node 20+)
# put the code in a.ts, then:
tsc --strict --target es2022 --lib es2022,dom --module commonjs a.ts && node a.js

By hand (Go):

# put the code in main.go with `package main`, the imports, and a main() that calls your example function
go run main.go

What was verified

Every code block in this guide was compiled and executed with TypeScript 6.0.3 (strict mode, Node 22) and Go 1.26.5 (the code uses only features available in Go 1.22 or newer, such as the built-in min/max), and the output was compared with the comments. Where testing found a real bug in a first draft (for example a signed-integer bug in the Bloom filter in file 28), the explanation says so, because the lesson is worth keeping.

3. The mindset: five habits that matter more than any single algorithm

  1. Ask first, code later. Restate the problem; ask about size, order, duplicates, and empty input.
  2. Say the slow way out loud. A correct O(n²) answer with a clear path to better beats silence.
  3. Name the pattern and say why. "The array is sorted, so I can discard from either end": a reason, not a guess.
  4. Trace before you declare victory. One normal case, one edge case, one tricky branch.
  5. State complexity with the reason. "O(n), because each index is added and removed once."

4. A study plan for 2 to 4 weeks

Assume 2 to 3 focused hours per day, 5 or 6 days a week. The plan has three layers: learn (read a file and work its problems), drill (redo problems from memory), and mock (timed, spoken practice).

The routine for every topic file

The "cover and recreate" rule. For each problem, after reading the solution, close it and write the solution again from nothing. If you cannot, you understood the explanation but not the idea; read the key-insight paragraph again, then retry.

3-week plan. Use the 4-week plan but merge week 1's days 2 to 3 and week 2's days 3 to 4, and give DP the full last week.

Weekly review (15 minutes each Sunday)

Keep a tiny log with four columns: problem · pattern · what I got wrong · date to redo. Redo each wrong problem after 3 days and again after 7 days. Patterns you repeatedly get wrong are your real study list.

How to run a mock interview

  1. Set a timer: 25 minutes for a medium problem, 40 for a hard one.
  2. Say everything out loud (or record yourself): restate, clarify, brute force, pattern, code, test, complexity.
  3. Do not look anything up for the first 15 minutes. If you are stuck, say what you would try, then take one hint.
  4. Afterwards, grade yourself with the table at the end of file 29's mock section.
  5. Write down the one thing to improve next time (usually communication or testing, not the algorithm).
Let the guide keep the schedule

Pick the 2-week or 4-week plan and a start date on the home page. Each day it shows what to study, and the problems you mark Needs redo come back after 3 and 7 days. That is the weekly-review log from this section, kept for you.

6. What this guide leaves out on purpose

Interviews at a few companies go further. When you finish, these are the next topics to study:

  • Range-query structures: Fenwick (binary indexed) trees and segment trees.
  • String algorithms: KMP, Z-function, rolling hash (Rabin–Karp), suffix arrays.
  • More graph algorithms: minimum spanning trees (Prim, Kruskal), strongly connected components (Tarjan, Kosaraju), maximum flow.
  • Advanced DP: DP on trees, digit DP, bitmask DP in depth, optimization tricks (monotone queue, convex hull trick).
  • Geometry and math: sweep-line geometry, number theory (sieve, modular arithmetic, fast exponentiation with a modulus).
  • Concurrency and system design: covered by their own interview rounds and not by an algorithms guide.
